# 配置写入、覆盖与恢复原理

工作台把共用资料翻译成目标客户端的原生配置。它不启动代理来假装所有 Agent 都支持同一套字段。

## 1. 取得本次配置的真实输入

平台模式通过主进程重新获取并验证 Key；BYOK 模式解密服务商，要求模型属于该服务商且处于启用状态。输入包括 client、model、protocol、baseURL、apiKey、modelSettings。

本次高级参数存在时会作为本次参数集合传入，并保留模型显示名；它不等于永久编辑服务商模型规格，也不是对所有已保存字段进行任意深层自动合并。界面会结合当前选中规格形成表单；最终以预览为准。

## 2. 校验和能力过滤

校验客户端 ID、模型字符、Key 长度、HTTPS / 本机 HTTP、协议枚举与 URL 中不可包含的部分。高级设置先做类型和数值关系校验，再按照 `client-capabilities.json` 过滤。

协议不匹配会直接中止，例如 Codex 只允许 Responses。被过滤参数通过 notice 说明未写入，不会在目标文件中捏造一个字段。

## 3. 读取原文件并生成新内容

已知配置路径支持部分环境变量覆盖，不接受用户任意路径写入。原文件通过 lstat 检查，拒绝目标文件本身是符号链接或非普通文件，单文件写入读取上限 4 MiB。现有格式无法解析时中止。

当前检查针对目标文件，不是对所有父目录做完整的符号链接沙箱；使用自定义环境目录时仍需确认该目录归属。

适配器对 JSON/JSONC、TOML、YAML 或 `.env` 分别生成新文本：

| 格式 | 当前处理方式 |
| --- | --- |
| JSON / JSONC | `jsonc-parser` 定点修改，尽量保留非目标字段与注释；被整体替换节点内部的旧内容可能消失 |
| TOML | 解析对象后序列化，保留未覆盖的值，但注释 / 排版可能变化 |
| YAML | 文档模型修改节点，尽量保留文档结构；特定节点替换仍可能覆盖旧内部内容 |
| Gemini `.env` | 只移除并重写指定两个变量，保留其他行；拒绝识别到的不完整多行旧值 |

## “复写”到底覆盖多大范围

目标通常是一个 OneLinkAI provider 或默认模型字段。Claude Code 会改当前默认模型及多种角色映射；Codex 会改顶层 provider 与默认模型；部分客户端会整体替换 `onelinkai` provider，因此该 provider 原有的其他模型可能被新的单模型定义替换。

WorkBuddy、VS Code 会按目标分组与模型 ID 合并；DSH 会更新特定 patch；Gemini 会合并模型定义与精确模型 override。**“只改需要的设置”不是“每次永远只加一个模型”。**各页有准确范围和生成结果。

## 4. 脱敏预览与编辑

内部计划保留真实 Key 和原文件字节；返回给页面的是文件路径、是否原来存在、脱敏的拟写入内容和 notice。DSH 凭据文件及 Gemini `.env` 使用专门的隐藏展示，避免带出原来的其他秘密。

写入预览中的普通配置文件可点击“编辑配置”修改，支持切换高亮和还原此文件。编辑稿在主进程按 JSON/JSONC/JSON5、TOML 或 YAML 解析校验；编辑写入会重新格式化，原始文件仍按字节备份。认证文件及环境凭据文件不开放编辑。密钥使用随机占位符，必须保留在原位置，实际密钥由主进程在写入时还原，不返回页面。格式错误可以修正后重试；配置来源、模型或参数变化后需重新预览。

预览令牌随机生成、只在该主进程存在、10 分钟有效，提交时从 Map 移除，因此不能重复提交。计划过多会清理旧计划；退出后全部失效。

## 5. 提交前冲突检查

提交以序列锁防止同一服务同时配置 / 恢复。逐文件重新读取，对比 SHA-256 与预览时原文；不一致则要求重新预览。不存在文件也以专用标识参与比较。

这个检查保护“预览后有人编辑”的常见情况，并非跨进程锁定到最终写入的文件系统数据库事务；极短时间内的并发改写仍需避免。

## 6. 保存原始备份

在 `userData/agent-config/backups/<操作ID>/` 创建目录。原来存在的文件保存为 `<序号>.bak`；原来不存在的文件以历史 `existed: false` 表示，恢复时删除本次新文件。

备份保存真实原始字节，可能包含旧 Key。它不等同于页面的脱敏预览，也没有自动继承 BYOK 密文文件的加密包装。

## 7. 原子替换并回读

每个目标先写同目录临时文件，权限 0600，再 rename 替换，最后回读 SHA-256 与计划比较。目录创建权限 0700。多文件按顺序写，不是操作系统提供的跨文件原子提交。

全部完成后才写 `history.json`，记录 ID、时间、Agent、模型、文件路径、备份索引、写后哈希与恢复状态。返回 `verified: true` 和 `verification: file-readback`。

## 8. 写入失败时回滚

对已修改文件倒序恢复原字节；本次新建的文件删除。失败回滚再失败时，明确返回错误及备份路径，用户可以手工处理。

仅生成预览不会写备份。已经创建的空目录或某些备份文件不一定随失败清理，不能把文件事务解释成整个用户目录完全不变。

## 9. 历史恢复

选择一条尚未恢复的记录，先核对所有当前目标文件的哈希仍等于当时写后哈希，然后核对备份存在。只要有一份后来被改过，就停止自动恢复，保护后续编辑。

通过后原来存在的恢复原字节，原来没有的删除，最后标记 restored 与 restoredAt。如果恢复中失败，会尝试把已恢复文件重新写回恢复前状态。

多次操作同一文件时通常按最近相关操作向前恢复；历史记录不是能任意跳转而自动合并冲突的版本控制系统。

## 写入成功不表示 API 成功

文件回读只验证文件；连接测试只验证一次协议请求；Agent 内实际会话还受项目配置、命令行参数、环境变量、旧会话、客户端版本与模型能力影响。建议每次配置后在目标 Agent 新建会话测试。
